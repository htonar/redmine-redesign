# Права доступа (permissions) - как их узнавать через Redmine REST API

Исследовательская задача: как клиенту узнать, что текущему пользователю
разрешено (удалить задачу, редактировать её и т.п.), чтобы прятать/дизейблить
контролы в UI заранее, а не только ловить 403 постфактум. Источник -
[официальная REST API вики](https://www.redmine.org/projects/redmine/wiki/rest_api)
и её подстраницы (Rest_Roles, Rest_Memberships, Rest_Users, Rest_MyAccount).
Всё, что описано ниже, уже покрыто нашей OpenAPI-спекой
(`api/redmine-openapi.yaml` → `src/api/schema.d.ts`) - дополнительно ничего
генерировать не потребуется.

## Итог: единого "что мне можно" эндпоинта нет

В Redmine REST API нет ресурса вида `/my/permissions.json`. Права нужно
собирать из трех источников и объединять на клиенте:

1. **Админ-флаг.** `GET /my/account.json` (уже используется в
   `AuthContext.fetchAccount` для валидации логина) отдает `admin: boolean`.
   Админ обходит все проверки прав - если `admin === true`, дальнейшие шаги
   не нужны, разрешено всё.
2. **Роли пользователя по каждому проекту.**
   `GET /users/current.json?include=memberships` отдает
   `user.memberships[]`, а в каждом membership - `project` и `roles[]` (`id`,
   `name`). Это уже **разрешенный** список: если у пользователя права идут
   через членство в группе (а не напрямую), они всё равно попадут сюда - не
   нужно отдельно резолвить группы через `/projects/{id}/memberships.json`
   (тот ресурс отдает членства **проекта**, включая групповые - подходит для
   админки участников, но не для вопроса "что можно мне").
3. **Права каждой роли.** `GET /roles/{role_id}.json` отдает
   `role.permissions: string[]` - машинные ключи прав (`"delete_issues"`,
   `"edit_issues"`, `"add_issues"` и т.п.). Список ролей (`GET
   /roles.json`) отдает только `id`+`name`, без permissions - краткая форма
   для дропдаунов, не для проверки прав. Детали нужно запрашивать по каждой
   роли отдельно (`GET /roles/{id}.json`), но ролей в инстансе обычно мало
   (3-10), и не меняются часто - можно закэшировать на сессию.

### Итоговый алгоритм для "можно ли пользователю X в проекте P"

```
admin?                                  -> да, можно всё
иначе: roles = memberships[P].roles     -> нет членства в P -> нельзя
       permissions = union(rolePermissions[r] for r in roles)
       X in permissions?                -> да/нет
```

Кэш `rolePermissions` строится один раз за сессию: собрать все уникальные
`role.id`, встретившиеся в `memberships[]`, и сделать `GET /roles/{id}.json`
для каждого (обычно 1-3 запроса, не N+1 на каждую проверку).

## Ключевые права для наших пробелов (см. CLAUDE.md, "Известные пробелы")

- `delete_issues` - удаление задачи. **Права "только свои" не существует** -
  это отличается от прав на заметки (`edit_own_issue_notes` есть, а
  `delete_own_issues` - нет). Значит для кнопки "Удалить" достаточно одной
  проверки `delete_issues` на проект задачи, без сравнения автора с текущим
  пользователем.
- `edit_issues` - полное редактирование (наша форма `IssueFormFields`).
- `add_issues` - создание задачи в проекте (кнопка "Добавить задачу").
- Смена статуса уже сделана правильно - `allowed_statuses` в ответе `GET
  /issues/{id}.json?include=allowed_statuses` это готовый ответ Redmine
  "какие переходы статуса вам доступны", отдельно вычислять права не нужно
  (workflow зависит не только от роли, но и от текущего статуса и трекера -
  переиспользовать чужую логику дешевле, чем дублировать).

## Важная оговорка: это UX, а не защита

Клиентская проверка прав нужна только чтобы не показывать заведомо
недоступные кнопки - она не заменяет серверную проверку. Реальное решение
всегда принимает Redmine (403 на неавторизованный запрос). Значит даже после
внедрения проверок в UI нужно оставлять обработку 403 от API как fallback
(на случай гонки: права отозвали между загрузкой страницы и кликом).

## Реализация

`AuthContext.can(permission, projectId)` - готово, кэш `rolePermissions` на
сессию. Применено (issue #12, полный список мест - см. историю коммитов):

- `edit_issues`/`delete_issues`/`add_issues`/`manage_files` - исходный набор.
- `add_issue_notes` - поле комментария на карточке задачи.
- `manage_issue_relations` - добавление/удаление связей между задачами.
- `edit_issues` (повторно) - привязка/отвязка родителя и подзадач (это PUT
  `parent_issue_id`, тот же контракт, что у формы редактирования).
- `add_issue_watchers`/`delete_issue_watchers` - добавление стороннего
  наблюдателя и снятие **чужого** наблюдателя; снятие **себя** правом не
  ограничено (Redmine разрешает self-watch/unwatch всем, кто видит задачу).
- `log_time` - право за проект, а не за страницу (диалог логирования сам
  содержит выбор проекта) - фильтруется список проектов, передаваемых в
  `LogTimeDialog`, тем же паттерном, что `add_issues` в `IssuesPage.tsx`.
- `edit_time_entries`/`edit_own_time_entries` - правка/удаление существующей
  записи трудозатрат (в Redmine оба действия проверяются одним правом, нет
  отдельного `delete_time_entries`) - вынесено в чистую функцию
  `canManageTimeEntry` (`src/lib/time-entry-permissions.ts`, с тестами).
- Вложения к задаче: загрузка - `edit_issues || add_issue_notes`, удаление -
  `edit_issues` (подтверждено по исходникам Redmine:
  `Issue#attachments_deletable?` - это `editable_by?`, без исключения для
  автора загрузки).
