# CLAUDE.md

Контекст для работы над проектом - что делаем и почему, чтобы не переоткрывать
решения заново в каждой сессии.

## Что это

Собственный React-фронтенд для Redmine поверх его REST API. Не форк Redmine, не
плагин - отдельное SPA, говорящее с любым Redmine-инстансом через `/xxx.json`
эндпоинты. Дизайн - по мотивам [Behance-концепта](docs/design.md), не штатный UI
Redmine.

## Стек и почему так

- **Vite + React + TypeScript**, npm - стандартный выбор, без экзотики.
- **API-клиент - свой, тонкий, поверх сгенерированных типов**, а не готовая
  npm-библиотека: `redmine-ts` и `axios-redmine` заброшены/deprecated (см.
  [docs/redmine-api.md](docs/redmine-api.md)). Вместо них - OpenAPI-спека
  [d-yoshi/redmine-openapi](https://github.com/d-yoshi/redmine-openapi) →
  `openapi-typescript` (генерация типов) → `openapi-fetch` (рантайм-клиент).
  Спеку обновлять релизами оттуда, не редактировать `schema.d.ts` руками.
- **UI-кит - shadcn/ui на Radix Primitives** + своя тема поверх (см. ниже про
  дизайн). Выбрано вместо полностью самописных примитивов - быстрее получить
  рабочий и доступный (a11y) результат, кастомизация цветов/шрифтов все равно
  нужна под референс.

## Заметка: TypeScript 6.0 и peer deps

Vite-шаблон подтянул TypeScript 6.0 (bleeding edge), а часть экосистемы
(`openapi-typescript`, CLI `shadcn`) еще требует `^5.x` в peerDependencies.
Это конфликт версий пакетов, не реальная несовместимость - поэтому в `.npmrc`
стоит `legacy-peer-deps=true`. Если при обновлении зависимостей конфликт уйдет
сам (экосистема догонит TS 6), `.npmrc` можно убрать.

## Важное ограничение: авторизация и 2FA

Redmine REST API **не поддерживает интерактивный 2FA-челлендж**. Если у
пользователя включена двухфакторная аутентификация, HTTP Basic по логину/паролю
жестко отклоняется сервером (`401`) - это защита от обхода 2FA через API, а не
баг клиента. Работает только **API-ключ**.

Решение: клиентское приложение авторизуется **только по API-ключу**
(`X-Redmine-API-Key`). Логин/пароль в `src/api/client.ts` поддержан на уровне
типов (Basic auth) на случай не-2FA сценариев в будущем, но экран логина в UI
предлагает только ввод API-ключа - не строить форму логин/пароль как основной
путь, она не будет работать для аккаунтов с 2FA (включая аккаунт автора проекта).

## CORS и прокси-бэкенд

Проверено вручную на реальном инстансе (redmine.codestetic.com): Redmine не
отдает `Access-Control-Allow-Origin` ни на обычный запрос, ни на preflight
`OPTIONS`. Браузер блокирует прямой fetch из SPA с ошибкой `Failed to fetch` -
это не редкий случай, а, похоже, поведение по умолчанию (в коре Redmine нет
встроенной поддержки CORS). Полагаться на то, что у пользователя CORS настроен
на сервере, нельзя.

Решение - свой прокси-бэкенд, `server/` (Node.js + Hono, отдельный пакет со
своим `package.json`, не часть фронтового билда):

- Клиент шлет запросы на `${VITE_REDMINE_PROXY_URL}/proxy/...` вместо прямого
  обращения к Redmine, с заголовком `X-Redmine-Target: <baseUrl>` - тот же
  адрес, что пользователь ввел на экране логина. Реализовано в
  `src/api/client.ts` (`proxyUrl` опция) и `src/contexts/AuthContext.tsx`
  (читает `VITE_REDMINE_PROXY_URL` из env, см. `.env.example`).
- Прокси форвардит запрос 1:1 в целевой Redmine и добавляет CORS-заголовки в
  ответе (`hono/cors`, origin из `ALLOWED_ORIGIN`).
- Таргет **динамический** (любой Redmine, не захардкожен), но целевой хост
  обязан быть в `ALLOWED_REDMINE_HOSTS` (см. `server/.env.example`) - иначе
  прокси превращается в открытый SSRF-прокси, который можно использовать для
  доступа к произвольным внутренним хостам. Без непустого `ALLOWED_REDMINE_HOSTS`
  прокси отклоняет вообще все запросы (500), это осознанный fail-closed.
- Если `VITE_REDMINE_PROXY_URL` не задан - клиент работает как раньше, напрямую
  (годится для локальной разработки или инстансов с настроенным CORS).
- Прокси не хранит и не логирует API-ключи - только форвардит заголовок
  `X-Redmine-API-Key` дальше, транзитом.

Запуск для разработки - два процесса: `npm run dev` в корне (фронт) и `npm run
dev` в `server/` (прокси). Оба нужны, чтобы реально сходить в чей-то Redmine.

## Структура

```
api/redmine-openapi.yaml   # OpenAPI-спека Redmine REST API (источник правды)
src/api/schema.d.ts        # сгенерированные TS-типы - не редактировать руками
src/api/client.ts          # фабрика типизированного клиента (createRedmineClient)
server/                    # прокси-бэкенд для обхода CORS (Node.js + Hono)
docs/redmine-api.md        # как устроена спека/клиент, как обновлять
docs/design.md             # дизайн-язык, палитра, компоненты из референса
```

## Права доступа (permissions)

- [x] Как узнавать права через REST API - исследовано,
  см. [`docs/permissions.md`](docs/permissions.md). Коротко: единого "что мне
  можно" эндпоинта нет, но и резолвить группы вручную не нужно -
  `GET /users/current.json?include=memberships` уже отдает role id по
  каждому проекту с учетом групповых членств, а `GET /roles/{id}.json`
  отдает `permissions: string[]` для роли (кэшировать на сессию, ролей мало).
  `admin: true` с `/my/account.json` обходит все проверки. Все нужные
  эндпоинты уже есть в сгенерированных типах (`src/api/schema.d.ts`).
- [x] **Реализация** - `src/api/permissions.ts` (`fetchPermissions`, см.
  алгоритм в `docs/permissions.md`), подключено в `AuthContext`
  (`projectRoles`/`rolePermissions` грузятся отдельным запросом сразу после
  логина/восстановления сессии, не блокируя сам вход; `can(permission,
  projectId)` - в контексте, `user.admin` обходит проверку). Использовано:
  кнопка "Удалить" на карточке задачи (`delete_issues` - права "только свои"
  не бывает, в отличие от заметок), скрытие "Редактировать"
  (`edit_issues`) там же, скрытие "Добавить задачу" на списке задач
  (`add_issues`) - только когда в Topbar выбран конкретный проект, при "Все
  проекты" право заранее не известно (проект выбирается уже внутри диалога
  создания) - кнопка остается как раньше. Клиентская проверка - это UX, не
  замена серверной: `deleteIssue` (`src/api/issues.ts`) отдельно ловит 403 и
  показывает понятную ошибку на случай гонки (права отозвали между загрузкой
  страницы и кликом). Проверено сквозным прогоном на локальном Redmine
  (docker-compose): у роли "Репортёр" (есть `add_issues`, нет `edit_issues`/
  `delete_issues`) кнопки "Редактировать"/"Удалить" не показываются, у
  админа - показываются, удаление реально прошло (`DELETE /issues/{id}.json`
  → редирект на список).
- [x] Заодно заменили `window.confirm` на нормальную модалку -
  `src/components/ui/alert-dialog.tsx` (добавлен через `npx shadcn add

  Использовано для удаления задачи (`IssueDetailPage`) и записи времени

## Бэклог: паковка в десктоп-приложение + CI/CD

Сейчас единственный способ запустить всё вместе локально - Docker
(`docker-compose.yml`, см. выше). Цель - десктопный дистрибутив (Win/macOS/
Linux), чтобы не поднимать три контейнера каждый раз ради обычного
использования. Ничего не реализовано, только направление:

- [ ] **Выбор обертки: Electron vs Tauri** - не решено, зафиксировать явно
  перед началом работы, а не молча брать первое попавшееся.
  - **Electron** - естественнее ложится на текущий стек (весь проект уже на
    Node/TS, включая прокси `server/` на Hono): прокси можно запускать
    прямо в main-процессе Electron (тот и так Node) вместо отдельного
    child-процесса - меньше движущихся частей при апаковке. Минусы -
    больше вес дистрибутива (бандлит Chromium+Node), это общеизвестный
    компромисс.
  - **Tauri** - легче и быстрее (нативный WebView вместо Chromium), но
    требует Rust-тулчейн в сборке, а прокси (Node/Hono) под Tauri нельзя
    выполнить "изнутри" - только как отдельный sidecar-бинарник (`tauri.conf.json`
    → `bundle.externalBin`), то есть Node все равно нужно тащить как
    отдельный упакованный исполняемый файл (например через `pkg`/`node-sea`)
    рядом с Rust-ядром. Больше шагов на сборку, меньше вес на выходе.
  - Независимо от выбора: фронт остается статикой (`vite build`, тот же
    артефакт, что и для nginx-образа), меняется только то, что его
    хостит/раздает и как поднимается прокси рядом с ним.
- [ ] **Прокси при паковке остается нужен** - десктопное приложение никуда не
  девает первопричину (Redmine без CORS, см. "CORS и прокси-бэкенд" выше) -
  прокси-процесс должен подниматься вместе с приложением на `localhost`
  автоматически (пользователь не должен ничего руками стартовать), а не
  оставаться внешней зависимостью, как сейчас в `README`/`docker-compose.yml`.
  `ALLOWED_REDMINE_HOSTS` в десктоп-сценарии, скорее всего, придется
  открывать под адрес, который пользователь вводит на экране логина,
  динамически - в отличие от сегодняшнего fail-closed списка под конкретный
  known-хостинг (см. `server/.env.example`) - иначе десктопное приложение не
  сможет подключаться к произвольному инстансу пользователя без пересборки.
  Требует отдельного решения, не текущего же `ALLOWED_REDMINE_HOSTS`
  как есть.
- [ ] **GitHub Actions** - сборка дистрибутивов по тегу/релизу (матрица
  win/macOS/linux), публикация артефактов в GitHub Release. Оформлять уже
  после того, как понятен локальный процесс сборки руками (`electron-builder`
  или `tauri build` в зависимости от выбора выше) - автоматизировать то, чего
  еще нет и что не проверено вручную хотя бы раз, преждевременно.

## Ключевые фичи (то, чем реально пользуются каждый день)

Это не декоративные экраны (Gantt, wiki, файлы) - без них продукт не выполняет
свою основную задачу. Приоритет выше всего остального в списке шагов.

### Список задач: фильтры, сортировка, сохраненные виды

- `GET /issues.json` - основной список. Ключевые фильтры: `project_id`,
  `status_id` (есть спецзначение `o` - открытые, `c` - закрытые),
  `assigned_to_id` (спецзначение `me` - "мои задачи"), `tracker_id`,
  `priority_id`, `fixed_version_id`. Сортировка через `sort=field:desc,field2`
  (например `sort=priority:desc,updated_on:desc`). Пагинация `offset`/`limit`
  (лимит максимум 100 за раз).
- Разделение "мои задачи" vs "все задачи проекта" - это просто разные пресеты
  фильтра (`assigned_to_id=me` + текущий `project_id`), а не отдельная сущность.
  Дефолтный вид при открытии раздела задач - "мои задачи", без выбора руками.
- Сохранение фильтров - два независимых источника, оба стоит поддержать:
  1. **Свои сохраненные виды** (наш функционал, не Redmine): пресет = имя +
     сериализованный набор фильтров/сортировки/колонок. Хранить в localStorage
     на первом этапе (ключ по URL инстанса + пользователю), т.к. Redmine REST
     API не дает создавать `Queries` через API - только читать. Это то самое
     "не гадать каждый раз, где мои задачи, а где чужие" - сохраненный вид
     открывается в один клик.
  2. **Родные Query Redmine**: `GET /queries.json` возвращает уже созданные в
     самом Redmine публичные/личные query пользователя. `GET
     /issues.json?query_id=N` применяет фильтры сохраненного query одним
     параметром (остальные фильтры в этом случае игнорируются - см. спеку).
     Если у пользователя уже есть query, настроенные годами в Redmine, глупо
     заставлять его пересоздавать их у нас - просто даем выбрать query_id.
- `GET /issue_statuses.json`, `/trackers.json`,
  `/enumerations/issue_priorities.json`, `/projects.json` - справочники для
  выпадающих списков в панели фильтров.

### Учет трудозатрат (time tracking)

- Просмотр: `GET /time_entries.json`, фильтры `user_id=me` (свои), `project_id`,
  `spent_on` либо шорткаты `from`/`to` (диапазон дат - готовые пресеты "сегодня",
  "эта неделя" и т.п. строятся поверх этого), `issue_id`. Дает список записей
  (дата, проект, задача, активность, часы, комментарий) - разбить по дням/неделям
  на фронте для читаемости, API отдает плоским списком.
- Создание записи: `POST /time_entries.json` с `issue_id` (или `project_id`),
  `hours`, `activity_id`, `spent_on`, `comments`. Быстрый ввод времени прямо с
  карточки задачи (issue) - это стандартный сценарий "закрыл кусок работы,
  сразу залогировал", не отдельная форма где-то в другом разделе.
- Правка/удаление своей записи: `PUT`/`DELETE /time_entries/{id}.json`.
- Список видов деятельности для дропдауна: `GET
  /enumerations/time_entry_activities.json`.
- Сводка "сколько наработал за неделю/месяц" - считается на фронте агрегацией
  списка `time_entries` по датам, отдельного summary-эндпоинта в API нет.
