# CLAUDE.md

Контекст для работы над проектом - что делаем и почему, чтобы не переоткрывать
решения заново в каждой сессии.

## Что это

Собственный React-фронтенд для Redmine поверх его REST API. Не форк Redmine, не
плагин - отдельное SPA, говорящее с любым Redmine-инстансом через `/xxx.json`
эндпоинты. Дизайн - по мотивам [Behance-концепта](docs/design.md), не штатный UI
Redmine.

## Стек и почему так

- **Vite + React + TypeScript**, npm - стандартный выбор, без экзотики.
- **API-клиент - свой, тонкий, поверх сгенерированных типов**, а не готовая
  npm-библиотека: `redmine-ts` и `axios-redmine` заброшены/deprecated (см.
  [docs/redmine-api.md](docs/redmine-api.md)). Вместо них - OpenAPI-спека
  [d-yoshi/redmine-openapi](https://github.com/d-yoshi/redmine-openapi) →
  `openapi-typescript` (генерация типов) → `openapi-fetch` (рантайм-клиент).
  Спеку обновлять релизами оттуда, не редактировать `schema.d.ts` руками.
- **UI-кит - shadcn/ui на Radix Primitives** + своя тема поверх (см. ниже про
  дизайн). Выбрано вместо полностью самописных примитивов - быстрее получить
  рабочий и доступный (a11y) результат, кастомизация цветов/шрифтов все равно
  нужна под референс.

## Заметка: TypeScript 6.0 и peer deps

Vite-шаблон подтянул TypeScript 6.0 (bleeding edge), а часть экосистемы
(`openapi-typescript`, CLI `shadcn`) еще требует `^5.x` в peerDependencies.
Это конфликт версий пакетов, не реальная несовместимость - поэтому в `.npmrc`
стоит `legacy-peer-deps=true`. Если при обновлении зависимостей конфликт уйдет
сам (экосистема догонит TS 6), `.npmrc` можно убрать.

## Важное ограничение: авторизация и 2FA

Redmine REST API **не поддерживает интерактивный 2FA-челлендж**. Если у
пользователя включена двухфакторная аутентификация, HTTP Basic по логину/паролю
жестко отклоняется сервером (`401`) - это защита от обхода 2FA через API, а не
баг клиента. Работает только **API-ключ**.

Решение: клиентское приложение авторизуется **только по API-ключу**
(`X-Redmine-API-Key`). Логин/пароль в `src/api/client.ts` поддержан на уровне
типов (Basic auth) на случай не-2FA сценариев в будущем, но экран логина в UI
предлагает только ввод API-ключа - не строить форму логин/пароль как основной
путь, она не будет работать для аккаунтов с 2FA (включая аккаунт автора проекта).

## Ключевые фичи (то, чем реально пользуются каждый день)

Это не декоративные экраны (Gantt, wiki, файлы) - без них продукт не выполняет
свою основную задачу. Приоритет выше всего остального в списке шагов.

### Список задач: фильтры, сортировка, сохраненные виды

- `GET /issues.json` - основной список. Ключевые фильтры: `project_id`,
  `status_id` (есть спецзначение `o` - открытые, `c` - закрытые),
  `assigned_to_id` (спецзначение `me` - "мои задачи"), `tracker_id`,
  `priority_id`, `fixed_version_id`. Сортировка через `sort=field:desc,field2`
  (например `sort=priority:desc,updated_on:desc`). Пагинация `offset`/`limit`
  (лимит максимум 100 за раз).
- Разделение "мои задачи" vs "все задачи проекта" - это просто разные пресеты
  фильтра (`assigned_to_id=me` + текущий `project_id`), а не отдельная сущность.
  Дефолтный вид при открытии раздела задач - "мои задачи", без выбора руками.
- Сохранение фильтров - два независимых источника, оба стоит поддержать:
  1. **Свои сохраненные виды** (наш функционал, не Redmine): пресет = имя +
     сериализованный набор фильтров/сортировки/колонок. Хранить в localStorage
     на первом этапе (ключ по URL инстанса + пользователю), т.к. Redmine REST
     API не дает создавать `Queries` через API - только читать. Это то самое
     "не гадать каждый раз, где мои задачи, а где чужие" - сохраненный вид
     открывается в один клик.
  2. **Родные Query Redmine**: `GET /queries.json` возвращает уже созданные в
     самом Redmine публичные/личные query пользователя. `GET
     /issues.json?query_id=N` применяет фильтры сохраненного query одним
     параметром (остальные фильтры в этом случае игнорируются - см. спеку).
     Если у пользователя уже есть query, настроенные годами в Redmine, глупо
     заставлять его пересоздавать их у нас - просто даем выбрать query_id.
- `GET /issue_statuses.json`, `/trackers.json`,
  `/enumerations/issue_priorities.json`, `/projects.json` - справочники для
  выпадающих списков в панели фильтров.

### Учет трудозатрат (time tracking)

- Просмотр: `GET /time_entries.json`, фильтры `user_id=me` (свои), `project_id`,
  `spent_on` либо шорткаты `from`/`to` (диапазон дат - готовые пресеты "сегодня",
  "эта неделя" и т.п. строятся поверх этого), `issue_id`. Дает список записей
  (дата, проект, задача, активность, часы, комментарий) - разбить по дням/неделям
  на фронте для читаемости, API отдает плоским списком.
- Создание записи: `POST /time_entries.json` с `issue_id` (или `project_id`),
  `hours`, `activity_id`, `spent_on`, `comments`. Быстрый ввод времени прямо с
  карточки задачи (issue) - это стандартный сценарий "закрыл кусок работы,
  сразу залогировал", не отдельная форма где-то в другом разделе.
- Правка/удаление своей записи: `PUT`/`DELETE /time_entries/{id}.json`.
- Список видов деятельности для дропдауна: `GET
  /enumerations/time_entry_activities.json`.
- Сводка "сколько наработал за неделю/месяц" - считается на фронте агрегацией
  списка `time_entries` по датам, отдельного summary-эндпоинта в API нет.
